# FAQ

## 1. Are you also running SSIS? How is the "SSIS" column generated? I don't see any SSIS pod running.

No — there is no real SSIS anywhere in this project, and never was. Real Microsoft
SSIS needs SQL Server Integration Services on Windows; nothing here runs that.
This is also true of the reference repo (`SSIS_NIFI-Migration-main`): its
"source" side is a hand-written Python simulator, not actual SSIS.

**How the "source" numbers in the comparison report actually get generated:**

`source/telecom_stream/gen/emit.py` is a single generator script that, for
each synthetic CDR it creates, does two things in the same pass:

1. Decides — by construction, since *it* is the one injecting the fault —
   whether this row is clean or should be rejected, and for what reason
   (e.g. "I just set `duration_sec = -1`, so a correctly-implemented SSIS
   package would flag this `BAD_DURATION`"). It writes that known-correct
   answer straight into source Postgres's `fact_calls` / `quarantine_cdr`
   tables.
2. Writes the *same row, stripped of any answer*, as a raw NDJSON file into
   the landing directory NiFi watches.

So "source" in the comparison isn't SSIS's output — it's **ground truth
computed independently of the NiFi flow**, based on the same business rules
(`UNKNOWN_SUBSCRIBER`, `UNKNOWN_TOWER`, `UNKNOWN_PLAN`, `BAD_DURATION`, valid
duration range 0–7200s) that are also encoded in `pkg_telecom_cdr.dtsx`.
It's the same "independent oracle" idea the reference repo uses in
`converter/scripts/verify_bulk.py`, applied at data-generation time instead
of as a separate verification script. Building a full second ingest engine
that reprocesses every landing file independently — which is what the
reference repo's `source/ssis_sim/stream_runner.py` actually does — was
judged more machinery than this demo needed; it's a documented scope
decision (see `emit.py`'s own docstring and `README.md`'s "Design decisions
worth knowing"), not an oversight.

**What "AGREES" in the report actually proves:** that NiFi's migrated flow
correctly implements the business rules as encoded, matching an
independently-computed correct answer, row for row.

**What it does not prove:** that a real Microsoft SSIS installation would
produce byte-identical output, since nothing in either repo runs real SSIS
to check against.

## 2. Where is the SSIS `.dtsx` being used?

The `.dtsx` is used exactly once — at **compile time**, not runtime. It is
not interpreted or executed by anything at runtime, by NiFi or by the
"SSIS side."

**Where it lives:** `jobs/telecom_cdr/pkg_telecom_cdr.dtsx` — a real SSIS
XML file, generated by `jobs/telecom_cdr/generate_pkg_telecom_cdr.py` (there
is no SQL Server Data Tools here to author it by hand).

**Where it gets read** — all inside `migrator/cli.py`, when `migrator
convert` / `migrator deploy` runs (i.e. `make migrate`):

1. `parse_file(str(job.package_path))`
   (`migrator/ssis2nifi/dtsx/parse.py`) — opens the actual XML and turns it
   into Python objects: components, connections, columns, properties.
2. `annotate(...)` / `derive(...)`
   (`migrator/ssis2nifi/catalog/`) — works out facts like "this Lookup's key
   column is `subscriber_id`" or "this OLEDBDestination writes to
   `fact_calls`" — read straight from the XML's own
   `SqlCommand`/`OpenRowset`/property values, nothing hardcoded.
3. `flowdef.build(pkg, bindings, ...)`
   (`migrator/ssis2nifi/emit/flowdef.py`) — combines that parsed structure
   with the catalogue recipes (`migrator/catalogue/components/*.yml`) to
   emit the actual NiFi flow — every processor, every connection, every SQL
   expression in `out/telecom_cdr.flow.json` traces back to a specific piece
   of this `.dtsx`.
4. `bindings.py`'s auto-generator also reads it — `pkg.connections` tells it
   which connection managers exist (`Telecom Landing`, `Telecom Warehouse`)
   so it knows what to bind without any table/column name typed anywhere.

After step 3, the `.dtsx` is out of the picture. The generated `flow.json`
is what actually gets deployed and runs on NiFi (`provision.deploy()`);
NiFi has no knowledge of SSIS or this file once it's imported.

**Note:** the source-side generator (`telecom_stream/gen/faults.py`) does
**not** read the `.dtsx` either — its business rules are separately
hand-written Python that happens to encode the same logic, checked by eye to
match what the `.dtsx`'s `ConditionalSplit`/`Lookup` components express (see
Q1).

## 3. How is reconciliation done? How does it dynamically read the schema?

Reconciliation is the `report/` pipeline — four stages, each feeding the
next: **introspect → capture → diff → render**.

### 3.1 `introspect.py` — discovers the schema, doesn't assume it

`describe_table(conn, "fact_calls")` runs two queries against Postgres's own
`information_schema` — not against any file in this repo:

```sql
-- every column, in order
SELECT column_name FROM information_schema.columns
 WHERE table_schema = 'public' AND table_name = 'fact_calls'
 ORDER BY ordinal_position

-- the primary key, if any
SELECT kcu.column_name FROM information_schema.table_constraints tc
  JOIN information_schema.key_column_usage kcu ON ...
 WHERE ... constraint_type = 'PRIMARY KEY'
```

For `fact_calls` this returns `primary_key = ["call_id"]` plus the full
column list — discovered from the live database at report-run time, not
typed into any Python file. Point the same function at a completely
different table from a completely different job and it returns that table's
actual PK/columns instead.

### 3.2 `capture.py` — builds the comparison SQL *from* what was discovered

```python
fact = introspect.describe_table(conn, compare_cfg["fact_table"])   # -> TableSchema(pk=["call_id"], ...)
scalars = {"fact_count": row_count(conn, fact.qualified)}            # SELECT count(*) FROM fact_calls
sets = {"fact_keys": key_set(conn, fact)}                             # SELECT call_id FROM fact_calls
```

`key_set()` doesn't know the column is called `call_id` — it does
`cols = ", ".join(table.primary_key)` and builds `SELECT {cols} FROM
{table}` with whatever `introspect.py` just handed it. For a different job
whose fact table's key is composite (e.g. `order_id, line_no`), the exact
same function would emit `SELECT order_id, line_no FROM order_items` with no
code change.

The reject-reason histogram is similar but one honest exception:
```python
f"SELECT {reason_column}, count(*) FROM {reject_table} GROUP BY {reason_column}"
```
`reason_column` / `reject_table` come from `job.yml`'s `compare:` block, not
introspection — "which column holds the rejection reason" isn't metadata
Postgres tracks the way a primary key is, so that one has to be *told*, not
discovered. Documented in `migrator/jobconfig.py`'s docstring.

### 3.3 `diff.py` — compares two captures generically

Both source and destination get run through the same `capture()` call
(once per connection), producing two identically-shaped dicts.
`compare_scalars` / `compare_sets` / `compare_histograms` do plain set/dict
arithmetic (`sa - sb` for "only in source," etc.) with zero awareness of
what a `call_id` or a `fact_calls` even is.

### 3.4 What this means concretely for `telecom_cdr`

`job.yml`'s `compare:` block only says:
```yaml
compare:
  fact_table: fact_calls
  reject_table: quarantine_cdr
  reason_column: reason
```
Three strings. Everything else — that `call_id` is the key, that there are
eight columns on `fact_calls`, what those column names even are — is
discovered live against whichever Postgres it's pointed at. That's what
lets the same `report/capture.py`, unmodified, correctly build `SELECT
call_id FROM fact_calls` for this job without `call_id` ever being written
anywhere in `report/`.
